# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-agent research pipeline: Literature → Interdisciplinary Literature → Hypothesis → Experiment Planner → Coder → Writer ⇄ Reviewer. Each stage searches papers, cross-pollinates them with adjacent fields, synthesizes and ranks hypotheses, plans experiments, generates+runs code, drafts a NeurIPS-style paper PDF, and reviews it against upstream ground truth. Built on [LangGraph](https://github.com/langchain-ai/langgraph) end to end — every one of the seven agents is internally a `StateGraph`, not just the top-level pipeline orchestrator, so every step (each LLM call, each deterministic check) is its own traceable/evaluable graph node.

Read [README.md](README.md) first — it documents the full architecture, per-agent I/O contracts, and CLI usage in detail. Don't duplicate that content in explanations; point there instead.

## Commands

```bash
uv sync                    # install deps
cp .env.example .env       # then fill in LLM_BASE_URL / SEMANTIC_SCHOLAR_API_KEY

uv run pytest                          # run all tests
uv run pytest tests/test_hypothesis_agent.py            # single file
uv run pytest tests/test_hypothesis_agent.py::test_name # single test

uv run research-pipeline <agent> ...   # run a pipeline stage, e.g.:
uv run research-pipeline literature "research question" --max-results 5 --download-dir papers
```

```bash
uv run pre-commit install          # one-time, wires the git hook
uv run pre-commit run --all-files  # ruff --fix, ruff format, mypy
```

Ruff (lint+format) and mypy are configured in `pyproject.toml`, but **only `src/research_pipeline/agents/coder/**` + `tests/test_{coder_agent,slurm_submit}.py` are in scope** — the per-hook `files:` regexes in `.pre-commit-config.yaml` enforce that. The other six agents are not lint-clean yet, so `ruff check src/` or `mypy src/` repo-wide will still report plenty; run them against `agents/coder/` only, or widen the regexes deliberately as part of bringing another agent in.

## Architecture

Seven agents live under `src/research_pipeline/agents/<name>/`, each self-contained with its own `schema.py` (output contract + `validate_output()`), `prompts.py`, `state.py` (a `TypedDict` threading that agent's inputs/intermediates/output through its graph), `graph.py` (`build_<name>_graph(...) -> CompiledStateGraph`, compiled with `MemorySaver()`), and `<name>_agent.py` (class + `run_<name>_agent()` entry point). Non-LLM logic (HTTP clients, batching, sandboxing, PDF I/O, citation resolution) is factored into separate modules within each agent package specifically so it's unit-testable without hitting an LLM.

Every agent is internally a `StateGraph`, in one of two shapes depending on whether it has constructor-injected dependencies:
- **Free-function nodes** (`literature/`): `nodes.py` holds plain functions with no injectable state, used because this is the only agent with no `chat_model`/mock-injection constructor.
- **Bound-method nodes** (`interdisciplinary_literature/`, `hypothesis/`, `experiment_planner/`, `coder/`, `writer/`, `reviewer/`): all six take `chat_model` (Coder additionally `network_check`/`gpu_check`/`max_fix_attempts`, Interdisciplinary Literature additionally `search_arxiv_fn`/`search_semantic_scholar_fn`/`search_core_fn` — its only three network calls, injected for the same reason) via their constructor, which tests rely on injecting fakes into — so their graph nodes are thin `self._node_x(state) -> dict` wrapper methods on the class, each delegating to an unchanged private helper of the same shape it had before the graph existed (`self._analyze_batch(batch)`, `self._attempt_once(...)`, etc.), rather than free functions. `.run()`/`.revise()` build the graph via a module-level `build_<name>_graph(agent)`, `.invoke()` it with a fresh `uuid4()` thread_id, and unpack the final state's `result` key into the same return dict as before this pattern existed. Fan-out shape follows what the step actually needs: `hypothesis`/`experiment_planner`/`interdisciplinary_literature` fan out over a *dynamic*-length list (batches / hypotheses / adjacent fields) via LangGraph's `Send` API, since nothing depends on completion order — `interdisciplinary_literature`'s conditional edge additionally returns a plain node name when that list is *empty* (no adjacent field was identified), since an empty `Send` list would otherwise strand the run with no path to its output; `reviewer` fans out over a *fixed* small set of independent checks via plain `add_edge` (like `literature`'s arXiv/Semantic Scholar/CORE fan-out); `coder`'s per-plan loop and per-attempt fix loop are deliberately **sequential cycles, not fan-out** — `_slurm_jobs_submitted` gates `CODER_MAX_SLURM_JOBS_PER_RUN` and depends on each plan seeing the true up-to-date count, which only a true sequential loop guarantees. A non-serializable value needed across nodes (e.g. Writer's `CitationRegistry`) is never put in checkpointed state — it's rebuilt deterministically inside the node that needs it from the plain-dict state that's already there.

Agents chain by **data shape, not by a shared orchestrator**: each `run_<name>_agent()` takes a plain dict/list shaped like the *previous agent's output* (not internal state), and validates it against that upstream agent's own `validate_output()` before doing anything else. Where a link is optional it's kept optional *additively* rather than by changing a contract: `interdisciplinary_literature`'s output puts its merged pool under `papers`, the exact shape `hypothesis` already consumed, so inserting it required no change to either neighbour's ingestion; `run_hypothesis_agent`'s `interdisciplinary_context` and `run_experiment_planner_agent`'s `hypothesis_ids` both default to "behave exactly as before". This means every link works identically in-process or decoupled via disk (read a previous run's JSON straight from `outputs/`). See README's "Chaining agents individually" section for the full code example.

Two orchestrators sit above the agents, neither an agent itself:
- **Writer/Reviewer loop** (`writer_reviewer_loop.py`): draft → review → revise → re-review, until the Reviewer reports zero issues and every quality score clears the threshold, or `max_iterations` is hit. It keeps every iteration's PDF and review for traceability, not just the final one.
- **Pipeline orchestrator** (`orchestrator/`, Graph-agent pattern): runs all seven agents end to end as one LangGraph, with the Writer/Reviewer cycle as a conditional edge routing on `overall_pass`. Its nodes are thin wrappers over the same `run_<name>_agent()` entry points — no agent logic is reimplemented there, and it reuses the loop's `route_feedback_to_sections`/`_consolidate_unresolved` rather than duplicating them. It is also the only place the run *narrows* to a single hypothesis: `run_planner_node` passes `hypothesis_ids=[hypothesis_output["selected_hypothesis_id"]]`, so the Coder executes one experiment rather than three, while the Writer and Reviewer still receive the full `hypothesis_output` (all 3, plus the ranking and why one won) as framing context. Narrowing lives here rather than in the Hypothesis Agent deliberately — that agent stays independently useful and always returns all 3. Both write-up nodes take their paper set from `_papers_for_writeup` (the interdisciplinary merged pool when present, else `literature_output`) rather than reading `literature_output` directly: a hypothesis grounded in a cross-field paper must be citable, and Writer and Reviewer must resolve citations against the *same* index or the Reviewer flags citations the Writer was entitled to make. Non-serializable dependencies (preconfigured `writer`/`reviewer` agents) go in `config["configurable"]`, never in state, which is checkpointed.

Key shared modules at the top level:
- `config.py` — all env-var settings (LLM endpoint, API keys, per-agent output dirs/defaults), loaded via `.env`.
- `llm.py` — single `get_chat_model()` factory used by every LLM-calling agent; swapping providers (e.g. to `langchain_anthropic.ChatAnthropic`) happens here only.
- `llm_json.py` — shared "invoke model, parse JSON, retry once with a repair prompt on bad JSON" helper, reused by any agent that wants structured output.
- `llm_sections.py` — the same contract (one repair retry, then raise) for responses that carry **source code**, over a delimited `===BEGIN <field>===` / `===END <field>===` format with no escaping anywhere: a real newline is a real newline, a real backslash is a real backslash. It exists because JSON string values force generated code through an escape round-trip the model performs by hand, which a small quantized model gets wrong constantly — the failure it removes had already accumulated three separate deterministic repairs (`llm_json._fix_invalid_escapes`, `_loads_lenient`'s `strict=False`, `sandbox._strip_redundant_line_continuations`). Only the Coder Agent needs it today, for every code-bearing call; anything asking the model for short structured fields stays on `llm_json.py`. `strip_reasoning` is imported from `llm_json`, not duplicated — the `<think>` problem belongs to the model, not to either transport.
- `checkpointer.py` — the one place a LangGraph checkpointer is constructed, same "one factory" rule as `llm.py`: all eight compiled graphs (seven agents + orchestrator) call `get_checkpointer()`, so no `graph.py` ever names a saver class and switching the whole pipeline to durable checkpointing is one env var. `CHECKPOINTER_BACKEND` picks `memory` (default, and byte-for-byte the old hardcoded `MemorySaver()`), `sqlite`, or `postgres`; both non-default backends sit behind an optional extra so a plain `uv sync` is unaffected. The saver is a memoized process-wide singleton because agent graphs are rebuilt per call (`.run()` calls `build_<name>_graph()` every time) — without that, each invocation would open and leak a fresh DB connection. One sqlite file is shared by every graph safely: checkpoints are keyed by `(thread_id, checkpoint_ns)` and every call site already mints its own thread_id. `get_node_cache()` lives here too, a singleton for the same reason, backing `CachePolicy` on the paper-search nodes. Both singletons being process-wide is right in production and wrong across a pytest session — one test's cached search result would otherwise be served to a later test whose injected fake then never runs — so `tests/conftest.py` resets them around every test via an autouse fixture; don't remove it. `pending_nodes(graph, config)` is the resume primitive both unattended entry points share: it returns the nodes a checkpointed thread still owes, so a caller invokes with `None` (continue) instead of its inputs (start over). Empty covers "new thread", "already finished" and "backend is `memory` in a fresh process" alike, which is why resuming needs no special-casing for the default backend — it simply never triggers. `webapp/runner.py` gets this for free (thread_id has always been the run_id), and the web UI exposes it as a Resume button on a failed/cancelled run — gated on `checkpointer.is_durable()`, because under `memory` there is nothing to resume *to* and relaunching would quietly redo the whole pipeline behind a button that says otherwise; the route re-checks the run's status rather than trusting the button, since a second runner on one run directory would interleave events and fight over the same thread_id's checkpoints; `batch.py` had to *persist* a thread_id in the manifest first, since its old per-question `uuid4()` was by construction an id no later process could ever ask for, and it only reuses a recorded id when the question at that index still matches — indices are positions in a file people edit between sweeps, and resuming the wrong thread would silently graft half a run about one question onto another.
- `cli.py` — argparse entry point; adding a new agent means adding a subparser here following an existing one.
- `webapp/` — optional FastAPI + polled-fragment UI (`uv sync --extra webapp`, `research-pipeline serve`) for starting a run and watching it stage by stage. It **reads** the pipeline and never changes it: progress comes from `graph.stream(..., stream_mode="updates")`, and `stages.py` only reduces each node's own delta to display fields — it calls the orchestrator's `should_continue_revising` rather than restating the routing condition. The server never runs pipeline work in-process; `runs.RunStore.launch` spawns `python -m webapp.runner <run_dir>`, which is what makes a run cancellable (SIGTERM), crash-isolated, survivable across a server restart, and able to get its own `CODER_EXPERIMENTS_DIR` (settings are frozen at import, so that can only vary per process). The server's only view of a run is the files under `runs/<uuid>/`, so anything the UI needs must be written there by the runner, not held in memory.
- `batch.py` — runs `orchestrate` over a file of research questions unattended (`orchestrate-batch`), for collecting many runs at once. Each question is an independent graph invocation with its own thread_id and output dir; a `flock`-guarded `batch_manifest.json` is rewritten after every question so a pre-empted job resumes without redoing finished work — at two granularities, both driven by that manifest: a finished question is skipped outright, and an unfinished one is retried under the *same* thread_id it recorded, so a durable checkpointer lets it continue mid-question rather than restart. A consecutive-failure circuit breaker stops a sweep when something systemic breaks. It is the only place in the codebase that broadly swallows a stage-level exception — one bad question must not end a 100-question run.

### Design principles specific to this codebase

- **Determinism over model judgment wherever verifiable.** Hypothesis outcomes (supported/refuted/inconclusive) are computed in Python from the Coder Agent's own `meets_success_criteria`/`status` fields, never left for the model to decide. Citation validity is enforced by resolving `[[cite:PAPER_ID]]`/`[[citet:PAPER_ID]]` markers only against papers the Literature Agent actually found — any other id is stripped and flagged, never printed. Same rule, same reasons, in the two newer places: the Interdisciplinary Literature Agent dedupes cross-field results on the Literature Agent's own doi/normalized-title key (imported from `literature/nodes.py`, not re-implemented — "are these the same paper?" must only ever have one answer here) and filters every bridge insight's `supporting_paper_ids` to ids actually in the merged pool; and the Hypothesis Agent's `selected_hypothesis_id` is *derived* from whichever ranking entry holds rank 1 rather than asked for as its own field, with `schema.validate_output` rejecting a ranking that isn't a permutation of 1..3 over exactly the generated ids. The model scores; Python decides what that score means. The Reviewer re-derives its own ground truth independently rather than trusting the Writer's summary, and checks citation/results/coverage deterministically (regex/dict-diff, no LLM) — only hallucination nuance and framing/tone honesty go to the LLM.
- **The Coder Agent doesn't submit SLURM jobs unless explicitly told to.** GPU-needing plans with no GPU detected in this process always get generated code plus a `run.sbatch` template for a human to review and submit — there's nothing to run them on locally. `high`-complexity plans get the same sbatch-only treatment by default, since `run.sbatch` targets a *shared* cluster where nothing should run unreviewed; `CODER_RUN_HIGH_COMPLEXITY_WHEN_GPU_AVAILABLE` (default **false**) opts into running them synchronously instead — exactly like `low`/`medium` — but only when a GPU is actually detected in this process (a Kaggle notebook, a Barkla node reached via `run_pipeline.sbatch`: single-tenant compute already attached to the pipeline, not a shared queue to jump), bounded by `CODER_HIGH_COMPLEXITY_TIMEOUT_SECONDS` rather than the low/medium timeout table. `low`/`medium` plans (and `high` under that opt-in) are executed synchronously with a bounded timeout (`CODER_LOW_COMPLEXITY_TIMEOUT_SECONDS`/`CODER_MEDIUM_COMPLEXITY_TIMEOUT_SECONDS`, resolved in `coder_agent.py` since `sandbox.py` reads no settings), and only after runtime probing of network/GPU availability (never hardcoded assumptions, since the same code runs on a laptop, a Kaggle notebook, or a Barkla compute node). Separately, `CODER_AUTO_SUBMIT_SLURM` (default **false**) opts into actually submitting whatever *did* get deferred to `run.sbatch`, for unattended batch sweeps — even then submission is refused unless `sandbox.static_safety_check` is clean, an LLM pre-flight review of the un-runnable code raises nothing, and both job caps hold — `CODER_MAX_CONCURRENT_SLURM_JOBS` (checked against `squeue`, so it holds across every process in a sweep, and a failed probe blocks rather than waves through) and `CODER_MAX_SLURM_JOBS_PER_RUN` (per-question). Anything that trips a gate falls back to the manual path with a `reason` saying which one.
- **A failure is classified by kind before anything decides what to do about it.** The Coder Agent's
  `diagnose.classify_execution_failure` splits a non-zero exit into what actually broke, and two
  kinds never reach the model: a package the code correctly imports is installed and the *unchanged*
  code re-run, and a run that exceeded its time or memory budget has its own cost knobs halved by
  `repair.downscale` and is re-run. Neither spends a fix attempt (`CODER_MAX_ENV_REPAIRS` bounds
  installs separately) because neither was a defect in the generated source — sharing one budget is
  how a production run spent all three attempts on a missing `pandas`. The converse case routes the
  other way: an import no package provides (`pymc3`, `pystan`) goes to regeneration carrying the
  replacement API, because installing there succeeds and changes nothing.
- **Synthetic data cannot be reported as evidence.** `agents/coder/provenance.py` resolves every
  input a plan declares to real or surrogate, and any surrogate sets `meets_success_criteria` to the
  string `"unknown"` — which `writer_agent.compute_hypothesis_verdict` maps to "inconclusive".
  Returning `False` would map to **"refuted"**, i.e. the paper claiming a refutation off numbers
  computed on invented inputs. The metrics are still reported and the model's own claim is kept
  under `model_reported_meets_success_criteria`; only the verdict is withheld. `CODER_DATA_DIR`
  stages real data the agent cannot fetch, which is what makes a real verdict reachable.
- **A failed attempt is made cheap before it is made rarer.** The first execution of a generated experiment is a *smoke run*: the same code with every known cost knob pinned to its floor (`repair.smoke_variant`), under `CODER_SMOKE_TIMEOUT_SECONDS` rather than the complexity timeout, so a defect anywhere in the program surfaces in seconds instead of after the full run — and so each round of the fix loop does too. It is deliberately asymmetric: it can end an attempt early but never let one through, so anything that passes it is still executed at full size and the smoke run's own `results.json` is deleted rather than read. A failure the shrinking could itself have caused (anything but a `diagnose.is_scale_independent` exception) is re-run at full size rather than reported. In the same spirit, a program that *parses* is not yet a program that can run: `sandbox.check_undefined_names` (pyflakes, `UndefinedName`/`UndefinedLocal` only) catches a helper that was referenced but never written before a venv is provisioned, where the same defect used to cost a full provision plus an execution plus a fix attempt.
- **Generated code that fails is diagnosed and regenerated, not abandoned.** Coder's fix loop — the `attempt -> snapshot_and_regenerate -> attempt` graph cycle in `agents/coder/graph.py` — feeds the concrete failure — compile error, lint finding, stdout/stderr tail, or the traceback `run.py` records in `results.json["error"]` — back to the model and retries, bounded by `CODER_MAX_FIX_ATTEMPTS` (default 3). Every stop condition is a real check's own verdict; no model judgment decides whether code is good enough. The one exception is the sbatch-only path (GPU-needing with no GPU present, or `high` complexity without the opt-in above), where nothing can be executed locally, so an LLM pre-flight review is the only signal available. Which budget a failure spends depends on whether anything was learned: a response that was malformed or hollow rather than wrong (`_STRUCTURAL_ERROR_SOURCES` — unparseable, a missing section, a function under the wrong name, a `pass` for a body) rendered, provisioned and executed nothing, so it draws on `CODER_MAX_STRUCTURAL_RETRIES` and leaves `CODER_MAX_FIX_ATTEMPTS` for the defect underneath — the production shape being a run that spent all three attempts on the model omitting a section. `compile_check` stays on the fix budget on purpose: a syntax error is a real defect in a real answer. Env-provisioning failures are deliberately *not* retried — a missing package isn't something regenerating the code can fix. Each failed attempt is snapshotted under `experiments/<hid>/fix_attempts/attempt_<n>/` and summarized in the output's `fix_history`. Two things bound what a regeneration is allowed to disturb. A check that *localizes* its failure — to a section it parsed on its own, or to a line the template's span map resolves back to one — asks the model for only those sections and reuses the rest verbatim (`coder_agent._target_sections`), because the fix prompt's "keep whatever already worked" is an instruction, not a guarantee: a production trace has attempt 1 correctly fixing a `ModuleNotFoundError` while attempts 2 and 3 each introduced a fresh syntax error somewhere they were never asked to touch. And because a fix loop is not monotonic, giving up reports the attempt that got *furthest* rather than the one that happened to be last, ranked by the same `_ERROR_STAGE_ORDER` that already defines "did this regeneration make progress" (`_best_candidate`; ties go to the final attempt, so a run that never regressed is untouched).
- **Generated experiments use real data where real data exists, and must never assume data is simply there.** Before each experiment is generated, the Coder Agent looks up one dataset matching the plan's `data_requirements` (Hub search, then the Hugging Face Dataset Viewer to confirm it's actually servable and read its true columns/first rows) and offers it to the model with the exact `/rows` REST URL — the viewer API rather than the `datasets` library, so nothing extra is installed into each experiment's throwaway venv and nothing is cached on shared scratch. It's a prompt enhancement, never a dependency: `CODER_ENABLE_HF_DATASET_SEARCH` (default true) gates it, it's only attempted when the runtime network probe succeeds, and every failure degrades to generating exactly as before. Independently of whether a dataset was found, `sandbox.check_data_fallback` enforces the prompt's long-standing "guard the read, fall back to synthesized data" instruction: it AST-parses the generated `load_data` and routes any unguarded `open`/`pandas.read_*`/`numpy.load` back through the fix loop as `missing_data_fallback`. Same principle as everywhere else here — the instruction existed for months and was silently ignored until Python checked it.
- **Node-level retry only where the node is idempotent.** LLM- and search-calling nodes carry `RetryPolicy(max_attempts=2)` as an outer net over the retries already below them (`llm.py`'s client `max_retries`, `clients.py`'s `_request_with_retry`, `llm_json.py`'s one repair round-trip) — it catches only what escapes those entirely. It uses LangGraph's default `retry_on`, which does *not* retry `ValueError`/`RuntimeError` and friends; that's deliberate, since a schema failure surviving the repair retry is persistent, not flaky. Nodes with side effects are excluded on purpose and say so in a comment: the Coder's `attempt`/`snapshot_and_regenerate` fix loop (a retry would re-execute generated code or re-provision a venv, and env-provisioning failures are deliberately not retried), `probe_environment`/`search_hf_dataset` (cheap probes that already degrade gracefully), `download_papers` (already partial-success tolerant — a node retry would re-download everything that succeeded), and every orchestrator node (each wraps a whole agent). `timeout=` is not used anywhere: every node in this repo is sync `def`, and LangGraph applies node timeouts only to `async def` nodes. Caching follows the same "pure step" rule — `CachePolicy` is on the paper-search nodes only, gated by `ENABLE_PAPER_SEARCH_CACHE`, and when off, the node compiles with no cache policy at all rather than a zero TTL.
- **Template splicing, not `str.format()`.** The Coder Agent's `run.py.template` is filled via plain string replacement because LLM-generated code routinely contains literal `{`/`}` that would break format-string substitution.
- **One model, one factory, one endpoint.** Every agent is LLM-powered and every one of them goes through `llm.get_chat_model()` — no agent constructs its own client, and none takes a per-agent model/backend override; all seven share one `LLM_BASE_URL`/`LLM_MODEL`. The only backend is an OpenAI-compatible HTTP endpoint, and the pipeline is wired specifically for that endpoint to be vLLM serving [Qwen3-Coder 30B-A3B-Instruct](https://huggingface.co/Qwen/Qwen3-Coder-30B-A3B-Instruct) (`scripts/slurm/run_pipeline.sbatch`/`run_llm_server.sbatch`), a sparse-MoE coding model with ~3B active parameters per token. It replaced NVIDIA Nemotron 3 Nano, and the difference that matters in code is that Qwen3-Coder-Instruct is **not** a reasoning model: it emits no `<think>` trace and its chat template has no `enable_thinking` variable, so `llm._extra_body` sends `chat_template_kwargs` only when `LLM_ENABLE_THINKING` is actually on (default off) rather than putting a field with no reader on every request. `llm_json.strip_reasoning` still strips a trace if one ever arrives, which keeps the reasoning-model path working if `LLM_MODEL` is pointed back at one. Served at **TP=1** with `--max-model-len 131072` — measured, not assumed: Barkla job 10274103 reported 56.93 GiB of weights and a 150,272-token KV cache on one 80GB card, so the second GPU in `--gres=gpu:2` stays free for generated experiments. Anything parsing raw model output must go through `strip_fences`/`invoke_json` (or `llm_sections.invoke_sections`, which reuses the same `strip_reasoning`) rather than doing its own fence regex.

### Adding a new agent

Copy either structural pattern above into `agents/<name>/`, then register a subcommand in `cli.py`. If it needs LLM calls returning structured JSON, reuse `llm_json.py` rather than reimplementing retry/repair logic — or `llm_sections.py` if the response will contain source code or any other multi-line verbatim text.

`agents/coder/` is also the template for the per-agent tooling rollout: a directory-scoped `AGENTS.md` covering only what's specific to that package (pointing here and to README.md for everything pipeline-wide), plus that directory added to the `files:` regexes in `.pre-commit-config.yaml`. Replicate both when bringing another agent under lint/type coverage rather than inventing a new scoping approach — and expect to fix that agent's existing findings in the same change, since the hooks block commits once its path matches.
